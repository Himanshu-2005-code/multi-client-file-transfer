\section{Introduction}

The purpose of this project is to build a simple multi-client file
transfer application using TCP sockets in Python. The application
follows a client-server model where multiple clients can connect to one
server and communicate with it using a custom application-layer
protocol. The main aim was to understand how application-layer
communication can be designed on top of TCP and how multiple
connections can be handled at the same time.

The server supports user login, maintains a list of active users, and
processes different commands sent by clients. Users can send private
messages, broadcast messages, upload files to the server, download
files stored on the server, and send a file to another online client
through the server. The server uses a separate thread for each
connected client, which allows multiple clients to stay connected and
perform operations concurrently.

The protocol uses simple text-based control messages in the form of
\cmd{COMMAND|FIELD|FIELD}. File contents are handled separately as raw
bytes with the exact file size specified before the transfer. This
makes it possible to use the same TCP connection for both normal
commands and file transfers.

The project was also tested with multiple clients, and performance
experiments were performed for round-trip time, broadcast latency, and
concurrent file downloads. These experiments helped in understanding
the difference between application processing time and actual network
delay, especially when using the local loopback interface.

\subsection{Key Design Decisions}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{One thread per client} on the server, coordinated
        through a single \cmd{clients\_lock}-guarded dict
        (\cmd{active\_clients}) mapping username $\to$ socket. This is
        what lets \cmd{MSG}, \cmd{BROADCAST}, and \cmd{SEND} look up and
        write to another client's live socket from a different thread.
  \item \textbf{Client read/write split}: a client's background
        \textit{reader} thread owns every \cmd{recv()} on the socket
        (including pulling file bytes off the wire for \cmd{DOWNLOAD}
        and \cmd{SEND\_INCOMING}), while the main thread owns every
        \cmd{send()}. Because TCP's two directions are independent,
        this needs no locking around the socket itself, and it lets the
        client display an incoming \cmd{MSG}/\cmd{BROADCAST}/file push
        at any time, even while the user is mid-typed-command.
  \item \textbf{Length-prefixed binary transfer}: control messages are
        line-delimited text, but file bytes are raw with an exact byte
        count announced beforehand --- avoids ambiguity between binary
        data and the \cmd{|}/\cmd{\textbackslash{}n} delimiters used by
        the text protocol.
  \item \textbf{\cmd{SEND} is a live relay, not store-and-forward}: the
        server pulls the file off the sender's socket and immediately
        pushes it to the target's socket without touching disk.
        Simpler and faster, at the cost of requiring the target to be
        online at send time.
\end{itemize}

\section{Implementation}

The application was implemented in Python using the built-in TCP socket
and threading libraries. The server creates a TCP socket, binds it to
the selected address and port, and continuously accepts new
connections. Whenever a new client connects, the server creates a
separate thread to handle that client. This prevents one client's
activity from blocking the others.

The server keeps the currently connected users in an
\cmd{active\_clients} dictionary. Since several client threads can
access this shared dictionary at the same time, a lock is used to
protect it. This helps avoid inconsistent state when users log in, log
out, or send messages to other clients.

The server uses blocking sockets because the application is relatively
small and the assignment requires threading. A thread-per-client
approach was easier to understand and implement than using
\cmd{select()} or \cmd{asyncio}. Each client connection stays open
during the session instead of creating a new connection for every
command.

For sending data, \cmd{sendall()} is used so that the complete buffer
is sent before the operation returns. On the receiving side, control
messages are read one byte at a time until a newline is found. This
matches the line-oriented protocol and allows the receiver to know when
a control message is complete.

File transfer uses a different method because file contents are binary
data and cannot safely be treated as text lines. The sender first sends
a control message containing the filename and exact file size. After
the server or receiver sends \cmd{READY}, the raw file bytes are
transferred. The receiver then reads exactly the announced number of
bytes. This avoids depending on the TCP connection closing to mark the
end of a file.

The client also uses two threads. The main thread handles user input
and sends commands, while a background reader thread performs socket
reads. This is necessary because the client can receive an incoming
message or file from another user even while the user is entering
another command. The reader thread handles unsolicited \cmd{MSG},
\cmd{BROADCAST}, and \cmd{SEND\_INCOMING} messages separately from
normal command responses.

The project was kept intentionally simple so that each part of the
socket communication and concurrency model could be understood and
tested independently.

\section{Experimental Results}

All measurements below are from a real run against a live server on
localhost (\cmd{127.0.0.1:5050}), one client machine acting as both
client and server (loopback). A real multi-machine network would add
real propagation delay and NIC-level bandwidth limits that loopback
doesn't have, so these numbers represent a best case, not a
real-network prediction.

\subsection{Test 1 --- RTT (1 client, request/response, 100 repetitions)}

\begin{verbatim}
Test 1: RTT over 100 requests
  min:    0.042 ms
  avg:    0.054 ms
  median: 0.047 ms
  max:    0.212 ms
\end{verbatim}

Sub-millisecond RTT is expected on loopback --- there's no physical
network hop, so the time measured here is essentially thread scheduling
and socket syscall overhead, not network latency. The \texttt{max}
(0.212~ms) being roughly 4$\times$ the \texttt{min} is consistent with
occasional OS thread-scheduling jitter rather than anything
protocol-related.

\subsection{Test 2 --- Broadcast Latency (server $\to$ 5 clients)}

\begin{verbatim}
Test 2: broadcast delivery latency to 5 clients
  avg: 0.685 ms
  min: 0.543 ms
  max: 0.821 ms
\end{verbatim}

Latency here is higher than the single-request RTT in Test~1, which
makes sense: a \cmd{BROADCAST} requires the server to iterate over 5
sockets and call \cmd{send\_line} on each one sequentially (see
\cmd{handle\_broadcast} in \cmd{server/server.py}) before any of the 5
receiver threads can even start reading their copy, so the last
receiver's timestamp includes the fan-out delay for every client
relayed to before it.

\subsection{Test 3 --- Throughput (10 clients downloading concurrently)}

\begin{verbatim}
1 MB file:
  total transferred: 10.00 MB
  elapsed:           0.035 s
  server throughput: 286.81 MB/s

100 MB file:
  total transferred: 1000.00 MB
  elapsed:           4.107 s
  server throughput: 243.46 MB/s

1000 MB (1 GB) file:
  total transferred: 10000.00 MB
  elapsed:           221.621 s
  server throughput: 45.12 MB/s
\end{verbatim}

Throughput drops sharply as file size grows --- from $\sim$287~MB/s at
1~MB to just $\sim$45~MB/s at 1~GB, roughly a 6$\times$ fall-off, not
the flat or gently declining curve you might expect from network
overhead alone. The likely cause is in \cmd{handle\_download}
(\cmd{server/server.py}): the server reads the \textbf{entire} file
into memory (\cmd{data = f.read()}) before sending it in one
\cmd{send\_exact} call. With 10 clients concurrently downloading a
1~GB file, that's up to 10~GB held in memory across 10 threads
simultaneously, which pushes the machine into heavy memory
pressure/paging well before the network itself becomes the bottleneck.
At 1~MB and 100~MB per client (10~MB and 1000~MB total resident at
once), memory pressure is much less of a factor, which is consistent
with those two runs both staying above 240~MB/s. A straightforward fix
would be to stream the file in fixed-size chunks (e.g.\ 1~MB at a time)
instead of loading it whole, bounding memory use regardless of file
size or client count --- noted here as a known limitation rather than
implemented, since it wasn't required for this assignment's scope.

\section{Challenges}

One of the main challenges was handling communication when multiple
clients are connected at the same time. The server has to maintain
information about all active users and allow one client thread to send
data to another client's socket. Using a shared \cmd{active\_clients}
dictionary with a lock made this easier to manage.

Another challenge was deciding how to separate normal protocol messages
from file data. Since TCP provides a continuous byte stream, simply
reading from the socket does not tell the receiver where one
application message ends. The solution was to use newline-terminated
control messages and include an exact byte count for every file
transfer. This made the file boundary clear to the receiver.

Client-side asynchronous messages were another issue. A client cannot
assume that every incoming message is a direct response to the command
it just sent. Another user may send a message, broadcast, or file at
any time. To handle this, the client uses a background reader thread
and distinguishes pushed messages such as \cmd{MSG}, \cmd{BROADCAST},
and \cmd{SEND\_INCOMING} from ordinary command responses.

There was also a logout-related problem during testing. The server
correctly closed the socket after sending \cmd{LOGOUT\_OK}, but the
client reader thread initially interpreted that close as an unexpected
server disconnection. This was fixed by using an \cmd{expected\_close}
flag so the client knows that the connection is being closed normally.

The throughput experiment also revealed a limitation in the
implementation. For downloads, the server currently reads the entire
file into memory before sending it. This becomes expensive when ten
clients request a 1~GB file at the same time. The results suggested
that memory pressure was contributing to the large drop in throughput
for the 1~GB experiment. A possible improvement would be to stream the
file in fixed-size chunks instead --- this was not implemented, only
identified as a proposed fix, since it wasn't required for this
assignment's scope.

\section{Conclusion}

\begin{reviewnote}
Before submitting: same note as above --- rewrite this in your own
words before it goes in the final submission.
\end{reviewnote}

This project gave practical experience with designing and implementing
an application-layer protocol over TCP. Instead of relying only on
existing protocols, the project required defining our own message
format, commands, responses, error conditions, and file-transfer rules.

The implementation also helped in understanding how TCP sockets work in
a real application. In particular, the project showed that TCP provides
a reliable byte stream, but the application still needs its own rules
for identifying messages and file boundaries. The use of
newline-delimited control messages and fixed byte counts for file
payloads was one of the main design decisions.

Another important part of the project was concurrency. Using one thread
for each connected client made it possible to support several clients
at the same time, while the client's reader thread allowed incoming
messages and file transfers to be handled asynchronously.

The performance experiments also showed that network performance is
affected by more than just the protocol itself. In the local loopback
tests, very small RTTs were observed, while larger file transfers
exposed memory and processing limitations in the implementation.
Overall, the project improved my understanding of TCP communication,
application-layer protocol design, file transfer, and concurrent client
handling.
